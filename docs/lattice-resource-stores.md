# Lattice logical namespaces and shared ResourceStores

Foundations 1.6.0 adds an explicit release-bound ownership declaration to
`DomainMeridianRequirements`. Existing owner-dot namespaces remain valid without
this member. The released `lattice-authoring` and `lattice-generation` namespaces
retain their names. `namespaceOwnership.namespace` matches `resourceNamespace`;
its `provider` repeats the exact owning `DomainSchemaProviderPin`, including the
distribution version and provider-bundle fingerprint. The provider belongs to the
domain's identity scope. Every owned Resource must refer to that provider.
Namespaces reserved for Foundations cannot be claimed; duplicate Resources,
conflicting owners/releases, floating releases and undeclared physical fields fail.

A domain uses `resourceStoreDependencies` to reference a shared
`configuration-artifact` store by `storeId`, exact `provider` and all five
`resourceFingerprints`. Foundations supplies the corresponding
`meridian.sharedResourceStores` declaration: `id`, closed `kind`, exact `provider`
and logical `resources`. This contract includes `object:resources.objects` and the
four structured Resources `channels`, `metadata`, `orphan-candidates` and
`provenance`. Missing stores, incomplete/duplicate Resources, provider drift and
ResourceDefinition drift fail before provider construction. A domain cannot claim
the shared provider as its own. This addition does not extend Application Metadata
service semantics.

`composeDomainRequirements(domain, sharedResourceStores)` validates and combines
these declarations using the public package API. Preserve the complete released
operation requirements, guarantees and limits when constructing each requirement.
The bundle fingerprint is pinned on the provider; each Resource's own fingerprint
is pinned on its schema requirement. Core SchemaDefinition, inner SchemaDocument,
Catalog, Adapter capability, physical and runtime-configuration fingerprints retain
their independent meanings. No fingerprint can substitute for another.

Foundations chooses physical placement through its existing `meridian.engines`
and optional `domainRuntimeSelections`. A domain consuming the shared store needs
both `structured` and `object` bindings. An explicit domain runtime selection must
supply both; omission never falls back to another domain's Engine. The shared
Resources are composed into the domain's selected runtime with Foundations as the
shared owner. Structured/audit Resources remain colocated; object Resources use the
object binding. The native Object Catalog and provider are included in that runtime.
The shared schema contract does not imply that separately selected physical stores
are identical. Physical identities, mappings, migrations, secrets and lifecycle
remain Foundations-owned and must be supplied and verified by the deployment.

Each runtime ConfigMap and distribution reference is returned with its Kubernetes
namespace. Secret/config file projections come from the same selected runtime.
Consumers must project the returned references into their workload namespace via
the approved delivery authority. Never reuse a Kubernetes reference by name alone
across namespaces. Logical related-Resource references retain their released
namespaces. The Model Configuration factory must supply its released
`AuthoringSchemaProvider`, as the wheel does not declare that provider as a generic
entry point; service composition remains the Lattice package's responsibility.

`FOUNDATIONS_LATTICE_EVIDENCE_DIR` saves the two rendered configurations when running

changed Resource pin. This is offline contract composition evidence. It does not
assert physical migration, service startup, data operations or lifecycle recovery;
those remain downstream Lattice onboarding acceptance. No AWS/production operation

consumer selection, not a universal Meridian release allowlist.
